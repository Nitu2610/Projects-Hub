# Backend Architecture

## 1. Overview

The backend is a REST API built using:

- Node.js
- Express.js
- MongoDB
- Mongoose
- JWT
- bcrypt
- express-validator

Its main responsibility is to handle:

- User authentication
- Role-based authorization
- Ticket creation and management
- Ticket assignment
- Ticket workflow validation
- Ticket filtering, sorting, and pagination
- Admin dashboard statistics

The frontend communicates with the backend through HTTP requests using Axios.

---

## 2. Backend Architecture

The backend follows a layered architecture.

The main flow is:

```text
Frontend
   ↓
Routes
   ↓
Middleware
   ↓
Controller
   ↓
Service
   ↓
Model
   ↓
MongoDB
```

The response travels back through the same layers:

```text
MongoDB
   ↓
Model
   ↓
Service
   ↓
Controller
   ↓
HTTP Response
   ↓
Frontend
```
Each layer has a specific responsibility.

For example, creating a ticket:
```text

   │
   ▼

   ▼

   │

   │
```

## 4. Layer Responsibilities
### Routes
Routes define the API endpoints and connect them with middleware and controllers.

Example:` POST /tickets` -> `authMiddleware` -> `authorizeRoles("customer")` -> `validation` -> `ticketController.createTicket`

Routes should primarily define:

-  HTTP method
-  URL path
-  Middleware
-  Controller

Business logic should not be placed inside routes.

### Middleware
Middleware processes requests before they reach the controller.
Important middleware includes:

#### Authentication Middleware - `authMiddleware`

Responsible for:

-  Reading the JWT from the Authorization header
-  Verifying the token
-  Extracting the user information
-  Attaching the authenticated user to req.user

Example: `Authorization: Bearer <token>` -> `authMiddleware` -> `req.user`  

### Role Authorization - `authorizeRoles`
Checks whether the authenticated user's role is allowed to access an endpoint.

Example: 
-  Customer → create ticket
-  Agent    → update assigned tickets
-  Admin    → manage all tickets

### Validation Middleware - `validationMiddleware`
Handles validation errors generated by express-validator.

### Async Handler - `asyncHandler`
Helps forward rejected asynchronous operations to the centralized error-handling middleware.

---

## 5. Controllers
Controllers handle HTTP-related responsibilities.

They:

-  Read request data
-  Read authenticated user information
-  Call the service layer
-  Decide the HTTP response
-  Return JSON to the client

Typical request data includes: `req.body` `req.params` `req.query` `req.user`

The controller should not contain large amounts of business logic or direct database operations.

Example: HTTP Request -> Controller -> Service -> Service Result -> HTTP Response

---

## 6. Services
The service layer contains the application's business logic.

Examples include:
-  Creating tickets
-  Retrieving tickets
-  Updating tickets
-  Deleting tickets
-  Checking ticket ownership
-  Checking ticket assignment
-  Validating ticket status transitions
-  Assigning agents
-  Building dashboard statistics

The service layer is also responsible for applying business rules before modifying data.

Example: Update Ticket -> Find Ticket -> Check User Role -> Check Ticket Access -> Validate Allowed Changes -> Update Ticket

This keeps business rules separate from HTTP handling.

---

## 7. Models
Mongoose models define the structure of documents stored in MongoDB.

The main models are: `User`  and `Ticket`

### Ticket
A ticket contains information such as:
```text
Ticket
├── title
├── description
├── issueOccurredAt
├── status
├── priority
├── createdBy
├── assignedTo
└── resolution
```

### Relationships
Tickets reference users using MongoDB ObjectIds.
```text
User
 │
 ├── createdBy ──────► Ticket
 │
 └── assignedTo ─────► Ticket
```
Mongoose populate() is used where related user information needs to be returned with a ticket.

## 8. Authentication
The application uses JWT-based authentication.

### Login Flow
```text
User
 ↓
Login Page
 ↓
POST /users/login
 ↓
Auth Controller
 ↓
Verify user
 ↓
Compare password using bcrypt
 ↓
Generate JWT
 ↓
Return token + user
 ↓
Frontend stores token
```
The JWT contains information such as:
```js
{
  id: user._id,
  role: user.role
}
```

### Authenticated Request
After login, the frontend sends the token with API requests: `Authorization: Bearer <JWT>`

The backend:
```text
Request
   ↓
authMiddleware
   ↓
Verify JWT
   ↓
Extract user ID and role
   ↓
req.user
   ↓
Next middleware/controller
```
This allows the backend to identify the authenticated user.

---

## 9. Role-Based Authorization
The application has three roles: `customer`,  `agent`, `admin`.
Authorization is handled at two levels.

### Route-Level Authorization
Determines whether a role can access an endpoint.

### Resource-Level Authorization
The service layer checks whether the user can access a specific ticket.

This is important because authentication only tells us who the user is.
Authorization determines what that user is allowed to do.

## 10. Ticket Update Workflow

Updating a ticket involves multiple business checks.
```text
Update Request
      ↓
Find Ticket
      ↓
Check User Role
      ↓
Check Ticket Access
      ↓
Validate Allowed Fields
      ↓
Validate Status Transition
      ↓
Validate Resolution Rules
      ↓
Update Ticket
```
The backend remains the final authority for authorization and business rules.

The frontend may hide or disable actions for UX purposes, but the backend must still enforce the rules.

---

## 11. Query, Filtering and Pagination

Ticket listing supports query parameters such as: `search`, `status`, `priority`, `sortBy`, `order`, `page`, `limit`.

The backend converts these query parameters into MongoDB query options.

Reusable utilities handle: `buildFilter()`, `buildSort()`, `buildPagination()`
This keeps query-building logic separate from the controller and service code.

Example: `GET /tickets?page=2&limit=6&status=Open`

---

## 12. Error Handling
Errors are handled centrally rather than implementing completely different error responses in every route.

General flow:
```text
Controller / Service
        ↓
     Error
        ↓
   asyncHandler
        ↓
next(error)
        ↓
Error Middleware
        ↓
HTTP Response
        ↓
Frontend
```

The frontend can then display an appropriate error message to the user.

Common HTTP errors include:
```text
400 → Bad Request
401 → Unauthorized
403 → Forbidden
404 → Not Found
500 → Internal Server Error
```

## 13. Frontend ↔ Backend Communication
The frontend uses Axios to communicate with the backend.

The frontend has a shared Axios instance:
```text
React Component
      ↓
Context / Page
      ↓
API Module
      ↓
Axios Instance
      ↓
Express API
```
The backend processes the request and returns JSON.

## 16. Important Backend Design Decisions
### Separation of concerns
Routes, controllers, services, models and middleware have separate responsibilities.

### Backend-enforced authorization
The backend does not trust the frontend to enforce security rules.
Even if a button is hidden in React, the backend verifies the user's role and access to the resource.

### JWT authentication
JWT allows the API to identify authenticated users without maintaining a traditional server-side session.

### Reusable query utilities
Filtering, sorting and pagination logic is separated into reusable utilities instead of being repeated inside controllers.

### Service layer for business logic
Business rules are kept in the service layer rather than being mixed with HTTP handling.

## Interview Explanation
- The backend is a REST API built using Node.js, Express, MongoDB and Mongoose. I use a layered architecture where routes define endpoints, middleware handles authentication, authorization and validation, controllers handle HTTP concerns, and services contain the business logic. Mongoose models handle MongoDB interaction.

- Authentication is JWT-based. After login, the server generates a JWT containing the user's ID and role. The frontend sends the token in the Authorization header, and the authentication middleware verifies it and attaches the user to req.user.

- I have three roles — customer, agent and admin. Authorization is enforced both at the route level and at the resource level. For example, an agent can update an assigned ticket, while an admin can manage all tickets.

- Ticket listing also supports filtering, sorting, searching and pagination. I separated the query-building logic into reusable utilities to keep the service layer cleaner.

- The main goal of the architecture is separation of concerns while avoiding unnecessary abstraction.
